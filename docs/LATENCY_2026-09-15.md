# Gateway latency measurements, 2026-09-15–16

The retained portable implementation improves the batched frame gateway workload
from **54.067 to 48.408 ns/message**, or **18.50 to 20.66 million messages/second**
in the principal 24-pair comparison. The median paired latency change is -10.53%,
with 23 of 24 pairs faster. This is an in-memory desktop measurement, not network
or exchange service latency.

The changes are safe flattened index access in book/risk and a specialized
single-maker fill path. They preserve fixed capacity, validation, matching/FIFO,
wire encoding, stable digests, and hot-path allocation behavior. Some workloads
regress; see the tradeoffs below. No native CPU flags are forced by default.
An optional benchmark-trained PGO build improves a separate 24-pair frame
comparison from 52.202 to 38.974 ns/message, with all pairs faster.

## Environment and comparison method

- Base commit: `29311d174734f6a3ff8016e90577fa67a634ffe3`; initially clean checkout.
- AMD Ryzen 7 7735HS, 8 cores / 16 logical processors.
- Windows 11 Home, build 26200; `x86_64-pc-windows-msvc`.
- Rust 1.96.0 (`ac68faa20`), LLVM 22.1.2.
- Existing release profile: fat LTO, one codegen unit, aborting panics.
- Portable release flags unless explicitly identified otherwise.
- Each paired comparison uses separate saved executables, logical CPU 2
  (affinity mask 4), alternating AB/BA order, and one excluded warmup run per
  executable. No benchmarks run concurrently with our builds or tests.
- The main table uses 24 pairs, with 136 cells in every complete suite run.
  All original 126 cells remain; ten batched cells were added to both baseline
  and candidate. No samples or slow runs are removed.
- Table latency is the median of each run's mean. Batched means are reconstructed
  from throughput computed using total elapsed nanoseconds before rounding.
  Paired percentages are medians of within-pair changes, so they need not equal
  the ratio of the two displayed medians.

The original unpinned executable ranged roughly 73–154 ns/message during early
runs. The reported 160–170 ns starting point was not consistently reproduced.
Only equivalent workloads in paired runs are used for optimization claims;
the old individually timed cell must not be compared to a new batched cell as
an optimization speedup.

Desktop scheduling, CPU frequency, thermals, and other applications affect these
results. Later exploratory comparisons encountered substantial background game
load. Those runs are identified separately; they do not replace the principal
portable comparison. The affected experiments were repeated on September 16
after the game stopped, using the same verified binaries and fresh output
directories (`*-quiet-pairs`). Hardware performance counters were not collected.

## Retained implementation and safety

### Flattened book and risk index access

Both indexes already store a logically flat table in nested fixed arrays.
Safe `as_flattened()` slices expose the same storage before indexing (two
flatten calls for book, one for risk), replacing coordinate reconstruction and
nested indexing expressions. Slot order, hashing, probe order, table
capacity, deletion/back-shifting, reverse handles, and memory layout are
unchanged. Rust still checks the final index. No allocation or unsafe code is
introduced.

### Single-maker fill

`OrderBook::submit` first performs the original validation in the original
order, including duplicate IDs and post-only rejection. If the best-price FIFO
maker can satisfy the whole taker, it checks report insertion before mutating
book state. A partial maker fill updates quantity and the level aggregate
directly; an exact maker fill uses the same removal/index-repair logic as the
general plan path. It avoids constructing a fill plan and then rereading the
maker for this case.

The taker is completely satisfied, so no resting-capacity check or rollback is
needed and FOK is atomic. Multi-maker fills and other orders retain the general
plan path. Existing reports are preserved, a full report buffer rejects without
mutation, and report counts remain per submission. Differential tests compare
both paths across sides, time-in-force values, partial/exact/multiple fills,
insufficient liquidity, colliding IDs, FIFO peers, and existing reports. A
separate test checks zero report capacity and rejection precedence.

The only public API extension is read-only `OrderBook::contains_order`, allowing
the benchmark to exercise the actual index lookup. Normal public submission
retains its duplicate check. No gateway, wire, SPSC, snapshot, or digest code
changes are retained.

### Batched measurements

Ten cells time 64 operations per interval after eight warmup batches. Inputs,
fixtures, report storage, verification, and digests stay outside the timer.
Operations and their observations use `black_box`; outcomes and final state are
checked. Allocation gates also cover fixture setup and validation. Throughput
uses accumulated raw time; integer nanosecond fields retain the existing schema.

The frame and normalized-command cells each process 32 complete rest/fill pairs
with `Gateway<2,8,2,2>`. Risk cells use `RiskEngine<64,128>` with 64 accounts;
reserve grows occupancy from 0 to 64 and fill reduces it from 64 to 0. Account
lookup includes `account_snapshot` exposure arithmetic; reservation lookup uses
`can_cancel`, including ownership validation. Book cells use `OrderBook<2,64>`;
single fill progressively consumes one 64-unit maker, with a separate report
buffer for every taker. This supplements the gateway's exact-maker-removal case.

**Batched percentiles describe distributions of 64-operation averages, not
individual-message tail latency.** Existing individually timed cells retain
their original methodology and coarse timer limitations. Some legacy lookup
cells also consume results weakly; their timings cannot isolate pure lookup
cost as reliably as the new observed batched cells.

## Tradeoffs and ablation

Adding single-fill handling to flattened indexes alone was tested in a separate
24-pair comparison (`single-ablation`). Batched frames improved 49.669 → 48.363
ns (-2.78% paired, 19/24 wins), the seeded gateway mix improved 91 → 88 ns
(-3.32%, 21/24), and book single fill improved 14.969 → 13.588 ns (-8.86%, 23/24).
However, normalized commands regressed 47.098 → 49.131 ns (+4.78%, only 2/24
wins). The fast path is retained for the requested frame gateway priority.

The complete 136-cell summaries are retained, including these regressions
against baseline:

| Existing cell | Baseline → retained ns/op | Median paired change | Slower pairs |
| --- | ---: | ---: | ---: |
| Risk cancel, occupancy 102 | 33 → 48 | +41.88% | 24/24 |
| Risk reserve, occupancy 102 | 38 → 46 | +19.47% | 24/24 |
| Book reprice | 61.5 → 65.5 | +7.36% | 16/24 |
| Book quantity increase | 63.5 → 67 | +5.92% | 17/24 |
| Book head fill, depth 1 | 38 → 41 | +5.26% | 21/24 |
| Book non-crossing, 128×8 | 63 → 65 | +3.21% | 15/24 |

These risk fixtures contain 102 reservations out of 1,024 capacity, about 10%
occupancy. Their regressions recur in the single-fill ablation: cancel
34 → 48 ns (+43.27%, all 24 pairs slower), reserve 39 → 46 ns (+17.72%, 23/24
slower). Cancel ranges are disjoint; reserve ranges overlap in this ablation.
Their repeated slowdowns cannot be explained only by occasional outliers.
The risk source is identical between these ablation binaries; compiler choices
or executable layout may contribute, but that attribution is not established.
The legacy observation caveat above limits isolated algorithm-cost claims.

The ablation also slows book crossing at sparse 128×16 (+5.77%, 21/24 slower)
and dense 64×32 (+5.31%, 23/24 slower), head fill at depth 1 (+5.06%, 20/24
slower), and batched order lookup (+4.53%, 20/24 slower). The result is a
workload-dependent optimization, not an across-the-board speedup.

## Remaining bottlenecks and next three experiments

The successful gateway path still performs duplicate-ID validation, reservation
index insertion/removal, maker/taker reservation lookups, account lookups, checked
risk arithmetic, and report handling. Multi-maker matching still constructs and
applies a plan. These are observed code paths, not a measured attribution of CPU
cycles. No hardware evidence of cache-miss cost was collected. This change does
not speculate on cold snapshot validation or weaken arithmetic checks.

1. Add observed, batched reservation-occupancy/collision fixtures and representative
   multi-maker gateway flows. Profile the consistent reserve/cancel regressions
   and test targeted inlining/layout choices against both gateway APIs.
2. Investigate a safe reservation handle passed through the existing trusted
   gateway call chain, with generation/ownership checks and explicit deletion
   invalidation, to avoid maker/taker reservation lookup duplication. Measure
   against full gateway flows before expanding the API.
3. Revisit duplicate admission with an unforgeable validation token or a book
   ownership boundary that covers restored/prepopulated state. The tested
   watermark approach adds overhead and did not justify retaining it. Any new
   approach must preserve standalone book validation and rejection precedence.

## Attempts not retained

The following frame numbers are from separate experiments, not the principal
table. Except for the earlier validated confirmation, these are the September
16 repeats under quieter conditions. The policy is to leave an unproven
candidate out; a tiny or inconsistent gain is not enough to expand the code.

| Candidate | Comparison | Frame ns/message before → after | Paired change / wins | Decision |
| --- | --- | ---: | ---: | --- |
| Validated book submission with maintained ID bound | Baseline, 24 pairs | 63.495 → 65.097 | +1.32% / 10 of 24 | Reverted; no consistent primary benefit |
| Account slot cached in reservations | Baseline, 12 fresh pairs | 54.622 → 53.479 | -0.55% / 9 of 12 | Reverted; marginal primary gain, original pair/mix each win only 6/12 |
| Decode each borrowed variant once | Baseline, 12 fresh pairs | 53.671 → 57.204 | +7.39% / 1 of 12 | Reverted; frame regression |
| Convert frame to `Command`, call `process_command` | Baseline, 12 fresh pairs | 54.291 → 54.744 | +0.99% / 3 of 12 | Reverted; no primary gain |
| Increment-and-wrap probe cursors | Retained build, 12 fresh pairs | 49.259 → 49.411 | +0.69% / 5 of 12 | Reverted; no primary gain |

The validated path retained a safe fallback duplicate lookup for arbitrary,
restored, and prepopulated books. It did not rely solely on gateway/risk
watermarks. Its direct-book rest and single-fill cells regressed about 4–5%.
The account cache used a private `u32` slot and checked account identity; it
did not change logical state/digests. Neither candidate remains in the source.
The account cache improves normalized commands by 2.82% paired (10/12 wins),
and cursors improve them by 5.11% (11/12 wins), but neither establishes the
requested frame improvement. Earlier noisy fresh retests are preserved in
`*-fresh-pairs`; the quieter data above supersede their tuning conclusions.

### Corrected experiment attribution

An audit discovered that restoring source snapshots with PowerShell `Copy-Item`
preserved older modification times, allowing Cargo to reuse some earlier
artifacts. The old isolated `risk-cache`, `decode`, `command-decode`, and
`single-fill` comparisons, plus `cursors-pairs` and `flat-index-pairs`, are
withdrawn as isolated optimization evidence. They remain labeled in the archive
for auditability. Old `final-portable.s` was also stale and is excluded.

The original/batched baseline, validated experiment, final portable comparison,
single-fill ablation, and native build have valid source/test inventories.
Corrected `*-fresh` experiments forcibly refresh all three experimental source
timestamps, record SHA-256 hashes, and rerun the full checks before benchmarking.
The corrected risk/decode/command test inventories confirm isolation. The final
verification repeats this process; generated assembly is `final-verified.s`.
The freshly rebuilt final executable's `.text` section matches the measured
`flat-index.exe` byte for byte; section hashes are retained in the archive.

## Compiler tuning

`-C target-cpu=native` was tested with the retained source and full correctness
checks. The first 24-pair comparison under background load was inconclusive
(`native-pairs`); the September 16 repeat is used below. Default portable
flags and Cargo profiles remain unchanged.

PGO used matching LLVM 22.1.2 tools, five full benchmark training runs, and
separate instrumented/optimized target directories. The merged profile contains
703 functions, 10,162 blocks, and 2,031,124,471 aggregate counts. The optimized
release build emitted no missing-profile warnings. Test binaries contain code
not covered by benchmark training and do emit LLVM profile warnings; their
tests still pass. These are workload-trained results, not evidence of an equal
gain for arbitrary production traffic.

| Build comparison, 24 pairs each | Frame ns/message | Frame paired change / wins | Normalized command ns/message | Command paired change / wins |
| --- | ---: | ---: | ---: | ---: |
| Portable → native | 49.230 → 46.834 | -5.94% / 19 of 24 | 50.423 → 50.523 | -0.28% / 12 of 24 |
| Portable → portable PGO | 52.202 → 38.974 | -23.91% / 24 of 24 | 52.167 → 37.921 | -27.81% / 24 of 24 |

PGO frame throughput is **19.16 → 25.66 M messages/s** in its matched comparison;
normalized-command throughput is **19.17 → 26.37 M messages/s**. Native and PGO
were tested independently, not combined. PGO is the stronger optional build
experiment here. No trained profile or host-specific setting is enabled by
default; the profile and reproduction script are retained in the evidence.

A direct original-source baseline versus retained-source PGO comparison

## Generated-code observations

The archive includes baseline and freshly generated final assembly plus extracts
of project functions reachable from the original `run_pair` benchmark. Neither
selected call graph contains hardware integer division instructions: these
power-of-two specializations already reduce modulo/coordinate arithmetic to
shifts and masks. The specialized frame path already eliminates the redundant
sequence decode, even though a more general frame instantiation repeats it.
This helps explain why the source-level decode/cursor proposals need measurement.

Static instruction counts for the same selected functions are:

| Function | Baseline | Retained |
| --- | ---: | ---: |
| Book index location | 334 | 225 |
| Book rest at tail | 465 | 342 |
| Book index remove | 155 | 104 |
| Risk index insert | 236 | 165 |
| Risk index lookup | 257 | 302 |
| Risk record fill | 257 | 209 |
| Gateway new order | 672 | 738 |

These are emitted instruction counts, not executed cycles or a cache profile.
The larger gateway and risk lookup functions also demonstrate the code-size
tradeoff; static shrinkage is not claimed everywhere. Gateway stack reservation
remains 200 bytes in this instantiation; risk record-fill stack reservation falls
120 → 104 bytes. The common book path avoids plan population, while general
matching still uses the existing plan. No unsafe bounds-check removal, unchecked
risk arithmetic, or speculative large storage change was introduced.

## Reproduction and exact files changed

The [evidence archive](evidence/latency-2026-09-15.zip) contains raw JSONL runs,
all-cell summaries, candidate snapshots/patches, check logs, final source,
baseline/final assembly, the PGO profile and training output, binary SHA-256
identities, and a manifest of archive member hashes. Its README distinguishes
valid comparisons from withdrawn exploratory attribution.

To repeat the experiments, extract the archive's `perf/` contents into
`target/perf/` in a checkout of the base revision. Use the included final
benchmark sources for both sides. Restore the baseline book/risk/gateway
snapshots, run `verify.ps1 -Stage baseline`, then restore the final book/risk
sources and run `verify.ps1 -Stage retained`. The verification helper refreshes
timestamps before each build. Run comparisons with:

```powershell
& target/perf/pairs.ps1 -Before baseline -After retained -Pairs 24 -Label reproduction-pairs
python target/perf/analyze.py target/perf/reproduction-pairs baseline retained
```

Use a new stage/output name for each experiment. The PGO script requires the
toolchain's `llvm-tools-preview` component and trains a fresh matching profile:

```powershell
rustup component add llvm-tools-preview
& target/perf/pgo-build.ps1 -Stage pgo-reproduction
& target/perf/pairs.ps1 -Before retained -After pgo-reproduction -Pairs 24 -Label pgo-reproduction-pairs
python target/perf/analyze.py target/perf/pgo-reproduction-pairs retained pgo-reproduction
```

The PGO helper scopes and restores environment flags. To reproduce native
builds, scope `RUSTFLAGS=-C target-cpu=native` around the verification helper,
restore it afterward, and compare the saved executables. No flags should be
changed while another experiment is building or running. The scripts assume
the tested Windows target and a repository path without spaces.
